# Sleep and lid control

OpenCharge separates four mechanisms: a public idle-system-sleep assertion, the global system sleep setting, a private lid-sleep control, and an idle-display-sleep assertion. An idle-system assertion allows lid/menu/low-battery sleep and does not implement closed-lid operation. See Apple's [public assertion API](https://developer.apple.com/documentation/iokit/1557134-iopmassertioncreatewithname).

The control page keeps the existing idle-until-target option and adds a separate **system/lid until target** opt-in, off by default. Hardware control must also be enabled. The display can be allowed to sleep independently. Active calibration requires idle, full system/lid and display sleep protection independently of the optional until-limit setting. Calibration draining/returning can therefore proceed with a closed lid. Ordinary manual and automatic discharge leave the separate public idle assertion controlled by the idle-until-target option; it is not forced on with that option off. A closed lid additionally requires full system/lid protection, independently of the optional until-limit setting. The former separate clamshell-discharge switch is removed; legacy saved values are ignored without changing the hardware-control opt-in. Reopening the lid releases the full override when the optional until-limit setting is off, while any explicitly selected idle protection remains during discharge. Unknown lid state conservatively requires full protection rather than silently dropping it. Confirmed thermal waiting below the effective target retains the selected idle/system until-target protections. Sailing holds and explicit manual pauses do not count as thermal waiting. The decision carries an optional typed thermal flag; the app does not infer activity from display strings. Top Up and departure preparation keep their effective targets during the wait. Lid edges request an immediate policy refresh during enabled control; the ten-second refresh remains a fallback. Duplicate observations and quit preparation do not start another event-driven refresh. Missing required helper support stops before charge commands. A failed full-sleep request disables hardware control, preserves possible cleanup ownership and attempts fixed restoration; calibration then requires an explicit continuation choice. The ordinary pause-on-sleep request follows the saved preference even when protection is required. Policy normalization disables the conflicting preference when optional system/lid-until-target is selected; an explicit in-memory value is not silently suppressed by control dispatch. Current charge/discharge decisions and physical adapter presence determine whether a session needs protection; completion, pause/restoration or explicit unplugging release it. Explicit physical disconnection releases protection. When raw adapter presence is unavailable, the same logical-connection or acknowledged-own-input-cut fallback used by the charge engine preserves protection; it cannot reliably distinguish a later unplug from an owned cut on such hardware. Exact thermal/sailing interactions and broader runtime policy fidelity remain unverified.

A compatible helper exposes only `sleepOverrideOn`, `sleepOverrideDisplayOn` and `sleepOverrideRestore` alongside the existing fixed commands. It requires a current charge session for enabling an override. **Inspect sleep interfaces** is read-only. The app requires exact `sleepOverride:interfacesDetected` and `sleepRecovery:phasesV1` capability fields. An older installed helper reports unsupported; it is not silently replaced. Interface detection checks symbols and a consistent stored/effective baseline, not physical effects or write permissions.

The independent transport dynamically resolves `IOPMCopySystemPowerSettings` and `IOPMSetSystemPowerSetting`, fixing the key to SleepDisabled. The [Apple implementation](https://github.com/apple-oss-distributions/IOKitUser/blob/main/pwr_mgt.subproj/IOPMEnergyPrefs.c) stores that setting in preferences. Lid suppression uses IOPMrootDomain scalar selector 12 with one Boolean value. Apple's [root user-client source](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/RootDomainUserClient.cpp) routes that operation to the powerd mask; the [root-domain implementation](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOPMrootDomain.cpp) shows a shared flag, not ownership per client. This can conflict with powerd or another controller and is experimental.

Before modification the helper synchronizes a separate `sleep-recovery.json` record in its private recovery directory. It shares the existing directory lock while remaining separate from charge/LED records. New records use schema 2, capturing the previous logical global value and pending fixed operations. Existing schema-1 helpers reject schema-2 records instead of ignoring their phases on downgrade. The new helper accepts schema 1 and migrates uncertain operations to schema 2 before compensating writes. An already-disabled global setting is preserved. Missing custom settings mean false, so restoration may leave an explicit false preference. The global journal distinguishes setting, active and restoring phases. Cleanup saves its restoring intent before calling the setter. A failed or interrupted setter is retried even if its cache reads false; a successful setter and readback must complete an uncertain operation. A confirmed active session still honors an externally released false value without another write. Older records with no phase are conservatively compensated. Lid cleanup clears the shared flag only for the recorded boot; an old boot's flag is discarded. The global record is deliberately recovered across reboot because preferences persist. Display assertion IDs are process-owned and are never replayed from disk.

Sleep overrides are not retained on quit, even when charge inhibition is retained. The helper also cleans them on console-user transition, sleep entry and a 45-second awake heartbeat timeout, and retries failed restoration. Within the current app run, failures stop new enabling attempts until charge control is explicitly disabled and re-enabled; release attempts remain retryable. Read-only inspection does not clear a failed-write stop state. Force Quit and hardware power loss cannot run application cleanup. A newly installed helper attempts recovery before new sleep actions. The development removal script preserves helper files and requests restart if a sleep-recovery marker survives shutdown, instead of silently abandoning persistent state. Do not downgrade/delete recovery records while an override is pending. The user installed the published 0.3.13 helper and authorized only read-only verification; its bytes match that published binary and its interface capability responds. It lacks the new recovery-phase protocol and is refused by 0.3.14 for full sleep control. Hardware and system actions remain off.

Fake/file tests and source inspection cannot prove real lid/display behavior, asynchronous powerd effects, kernel compatibility, actual reboot recovery or multi-controller isolation. Current development packages remain ad-hoc signed and not notarized. See [status](STATUS.md) and [verification](TESTING.md).


## Charging temperature and ordinary discharge

Charging-temperature protection does not mask an ordinary manual or automatic discharge request. Ordinary daily charging and discharge targets compare whole percentage bins from single-precision readings: an 80% discharge target completes at 80.6%. Fractional Sailing restart boundaries remain separate. Discharge stops at its target or reserve and still requires compatible full protection with a closed or unreadable lid. A stale charging-temperature window is cleared when entering discharge. Confirmed unplugging ends manual discharge so reconnecting does not re-arm it; an acknowledged input cut alone does not count as unplugging. The optional calibration-temperature enhancement remains separate. If the reserve is higher than the requested target, reaching the reserve holds charging off rather than repeatedly allowing a recharge above the lower target. If a reserve exit needs charging below the target, that charging still observes temperature protection; manual discharge is marked complete even when a temperature wait delays recharge.

## Ordering required protection

For a session requiring full system/lid protection, the app first checks helper capabilities. A fresh session first establishes inhibition because the helper requires a current charge session before enabling sleep protection. The app then establishes any required idle assertion and waits for the fixed sleep-override acknowledgement before publishing the sleep-entry policy or issuing the requested charging/discharging action. Failure during preparation restores possible bootstrap ownership and stops before starting charging or discharge. Completion applies its ordinary charge decision before releasing idle/full protection. A capability response by itself does not establish protection. If enabling protection fails, control is disabled and fixed restoration is attempted; the charge action is skipped. If a subsequent charge command fails, the existing cleanup path also restores the protected session. Sessions no longer requiring protection release it after applying the ordinary charge decision. The periodic refresh sends one enabling request, not a second duplicate request after the charge command.

## Optional lid locking

A separate, default-off option requests a lock when the lid is closed during an acknowledged full sleep override in the current user's active console session. It can be used during required calibration protection as well as optional until-limit protection. Each observed closed interval allows at most one attempt, including failures; reopening the lid rearms it. Missing lid state does not invent an open event. Enabling the option or starting a protected session while already closed can issue the first request. Read-only interface inspection does not rearm it.

The read-only observer subscribes to the root-domain general-interest clamshell message described in [Apple's IOPM header](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/IOKit/pwr_mgt/IOPM.h). It reads the current Boolean property rather than treating unrelated power notifications as closures. The existing refresh is also a fallback. Session gating uses [CGSessionCopyCurrentDictionary](https://developer.apple.com/documentation/coregraphics/cgsessioncopycurrentdictionary%28%29), requiring a completed foreground login for the current UID. The fixed `SACLockScreenImmediate` login-framework entry is resolved dynamically; [this upstream lock utility](https://github.com/sindresorhus/macos-lock/blob/main/lock.c) independently uses that no-argument entry. It is private SPI, has no success result and is not a guaranteed stable API. OpenCharge reports a request rather than claiming the screen is locked. No automatic unlock, alternate lock simulation, credential handling or root command is added. Actual locking remains unverified. Portable backup import disables this opt-in.


## Full-charge top-off

For an ordinary 100% target or Top Up, a full-charge decision keeps charging available to macOS instead of forcing inhibition. The separate full-charge flag releases selected until-target protection even when a single-precision reading rounds to 100% just below the stored double value. A later reading below full may require the selected protection again before charging commands. Calibration retains its independent full/display requirement. Temperature pauses are still evaluated separately. The menu bar describes active full-charge policy as system-managed top-off; monitoring continues to show observed charging. No physical charging or sleep effect is implied by this software state.


## Ordinary charging at sleep entry

In development source, the ordinary backend treats pause-on-sleep as an explicit opt-in. With it off, sleep entry releases owned sleep protection without sending an additional charge setter or a full charge restore. The previous charge session, recovery journal and sleeping lease remain owned. This specifies software requests; it does not guarantee how macOS or the hardware treats charge registers or adapter input during actual sleep.

With the option on and a current owned charge session, inhibition is attempted before protection is released. Protection release is still attempted if inhibition fails. The root helper reports failures and attempts existing recovery; failed recovery remains pending. A policy request alone cannot create a new charge session at sleep entry. Numeric firmware keeps its separate sleep projection, and selected multi-display Discharging entry keeps its separate allowance/protection/activity behavior.

Updated clients with the event-context capability defer sleep preparation to the root observer. The legacy app notification path follows the same ordinary ordering and retries failed protection release without modifying saved policy. An older helper can still execute its earlier forced-discharge fallback, so matching updated source is required for the complete behavior. No installed service or hardware setting was changed to validate this source increment.

# App localization

The interface supports only English (`en`) and Simplified Chinese (`zh-Hans`). The packaged app declares English as its development language and uses macOS language selection, including per-app language preferences. Relaunch the app after changing its language preference. Unsupported language preferences use native fallback; no other translation tables are included. Additional languages are outside the project scope.

`Resources/<language>.lproj/Localizable.strings` contains 604 source keys for controls, menu labels, status text, error descriptions and policy explanations. `AppShortcuts.strings` contains five invocation phrases with the named `${applicationName}` token. English plural rules cover local sample counts and minute durations. These are independently authored translations of this project's interface.

SwiftUI, AppKit-facing strings and domain labels use native localization APIs. Literal labels use `NSLocalizedString`. Formatted labels use the existing source format key through `String.localizedStringWithFormat`, with explicit signed 64-bit or unsigned 32-bit arguments where required; string arguments and escaped percent signs retain their positions. Page titles are localized separately from stored page identifiers. Charge mode, phase, command, configuration and schedule identifiers retain their existing values. Older history entries and raw replies from an older service can still contain their original language; this change does not rewrite saved history or localize the fixed IPC protocol. CLI help remains separate from the interface tables.

## Development checks

Run `bash Scripts/test-localization.sh` with the existing Swift tools and Python 3. The script compiles localization-key extraction for the app and its domain modules, combines compiler extraction with validated literal Foundation calls and checks complete coverage of Chinese source keys in both supported language tables, checks format placeholders and plural rules, and verifies named App Shortcut tokens against the source declarations.

It then builds a private, never-shown native bundle and runs its actual page/menu/domain labels, production minute-duration formatter, interpolated text, plural forms, error and policy explanation under English, Simplified Chinese, regional English/Chinese selections, a supported secondary language and an unsupported language. It compares all 39 unique formatted app keys against native interpolation using four signed/unsigned/string samples per key, including percent-containing and Unicode arguments. It requires identical encoded charge policy across all six runs. These checks do not launch the application, instantiate its runtime model, perform an intent, modify language preferences or call a hardware service. The full `Scripts/check.sh` includes the native check. Set `OPENCHARGE_TEST_ARCH=x86_64` or `arm64` to compile and execute an explicit architecture; an Intel run on Apple silicon requires Rosetta.

`Scripts/localization-resources.py` requires exactly the two supported language directories. Native packaging copies them before metadata extraction and code signing, and both native and universal packaging verify their declarations and exact file contents. Native bundle lookup and compiler coverage do not prove every translated layout, VoiceOver label or live Shortcuts/Siri phrase. Those visual and system-integration checks remain unverified. Existing release packages and the installed app are not updated by a source-only change.

Apple references: [Preparing views for localization](https://developer.apple.com/documentation/swiftui/preparing-views-for-localization) and [Migrate custom intents to App Intents](https://developer.apple.com/videos/play/tech-talks/10168/) describe the native string and App Shortcut phrase mechanisms used here.

Application, policy and hardware lookup calls use Foundation APIs available in macOS 11. The interpolated HTTP status uses the existing `%lld` key and an explicit signed 64-bit argument through `String.localizedStringWithFormat`. The existing resource keys are unchanged. Newer App Intents declarations retain their native framework types. The later macOS 11-target application build includes the guarded compatibility paths and packaged runtime. These lookup checks and current-host compilation do not establish actual macOS 11/12 runtime behavior.

Display dates use a separate formatter that preserves the current numeric date/time, abbreviated date/time and time-with-seconds styles. The macOS 11 path uses localized DateFormatter patterns, including a full calendar year for numeric dates. Calendar, locale and time zone are explicit inputs; formatting does not change stored dates or schedule calculations.

# Software updates

Open **OpenCharge → 检查更新…** or the software-update card in settings. Manual checks use the current bundle version. Automatic checks are off by default; when enabled, the app checks at launch when due and polls the due time hourly, with at least 12 hours between attempts. The app must be running. A newly available version opens the update window; downloading still requires a click. Repeated manual attempts are limited to once per minute. Clock rollback makes the next attempt due rather than suspending checks indefinitely.

Development previews are included by default because current releases are previews. Turn this off to consider only releases with neither a GitHub prerelease flag nor a SemVer prerelease suffix. No stable release is reported honestly when that channel is empty. Draft releases are ignored. Version precedence follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html); release date and API ordering do not decide the newest version.

The app anonymously lists releases from the fixed `shengjk/OpenCharge` repository using the [GitHub releases API](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28), including pagination. It does not use the latest-release endpoint because that excludes previews. Checks accept at most five pages of 100 releases and 2 MiB per page; hitting the full-page limit reports an incomplete check. An Apple Silicon build prefers `OpenCharge-macOS-arm64.zip`, falling back to the universal ZIP; an Intel build requires `OpenCharge-macOS-universal.zip`. Missing assets on the newest version do not silently select an older version.

**Download and verify** fetches the selected ZIP and `SHA256SUMS.txt`. Links must identify that repository, tag and fixed filenames. HTTPS requests and redirects are limited to GitHub's API/site and explicit release-asset hosts. Each archive is limited to its declared size and at most 64 MiB; checksum files are limited to 64 KiB. The app verifies exact byte count, SHA-256 and the [asset API digest](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28) when available. Missing, malformed or conflicting hashes fail the download. No account, cookie or GitHub token is used. Battery readings and device identifiers are not sent. GitHub receives ordinary connection metadata, including the source IP; the user agent is `OpenCharge`.

Successful ZIPs are stored in `~/Library/Caches/org.opencharge.app/Updates/` in separate private directories, with macOS web-download quarantine metadata set using the public URL resource API. Failed attempts remove their new directory. **Show in Finder** reveals the ZIP. Unzip and replace the application yourself using normal system checks; the app never launches the archive, replaces itself or installs/restarts the privileged service. The system can purge cached files. Battery data remains in Application Support; update preferences use local UserDefaults.

These checks establish consistency with the files published by the same GitHub repository. They do not independently authenticate the publisher or replace a signed/notarized installation chain. Current development builds are ad-hoc signed and not notarized. Fully automatic signed installation remains unfinished. See [status](STATUS.md) and [verification](TESTING.md).

The development transport uses URLSession delegate streaming, with the same response and byte limits for memory and file destinations. Disallowed redirects terminate immediately. Task cancellation closes the transfer and its file handle; hash verification also observes cancellation. A cancelled or failed verified download removes its newly created package directory. These networking APIs compile with a macOS 11 target, but the complete packaged application still requires macOS 13 pending other compatibility work.


## Signed-updater integration — work in progress

The `feature/signed-updates` branch adds a checksum-pinned Sparkle dependency and build-time public-key configuration guards. The application now selects an SDK adapter only when strict public-key metadata is configured; unconfigured development packages keep the manual route. Invalid configured metadata refuses update checks. Native and universal build scripts now embed the pinned framework, retain only English and Simplified Chinese resources, preserve its required versioned aliases, and sign nested components before signing the app. Release ZIP creation preserves only the eight validated framework aliases; unrelated symbolic links remain rejected. The adapter uses normal application termination, retaining the existing QuitFlow and service-maintenance gate. Local feed preparation, authenticated stable/preview history merging and signature finalization are implemented. Publication coordination and actual signed replacement/relaunch verification remain unfinished. These development packages are not a completed automatic-update distribution route.

Missing public-key configuration retains the manual-download route. The SDK adapter keeps automatic checks/downloads opt-in, mirrors preference changes made in the native update UI, filters stable/preview channels, disables external release-note downloads and fixes the feed independently of saved SDK preferences. Enclosures must identify the matching version of the official repository, a supported architecture-specific ZIP, a bounded size and a full application installation; package and delta routes are rejected. A prepared install remains a settings-reset barrier after the active SDK check session ends. Normal update termination uses the same cleanup and maintenance checks as a user quit. Configured metadata requires the fixed repository feed, archive verification before extraction, signed feeds without validation expiry, disabled profiling/JavaScript and opt-in update behavior. The configuration scripts never generate or read private signing keys.

The pinned dependency is [Sparkle 2.9.6](https://github.com/sparkle-project/Sparkle/releases/tag/2.9.6). Its official package checksum was verified and an isolated nonstarted updater loaded on both architectures on the current host. This is not an installation test or an older-system runtime test. Core configuration, temporary metadata-file fixtures and real-framework packaging fixtures passed. The latter exercise both architectures, ZIP extraction, nested signatures and actual English/Chinese resource lookup without starting an updater or installer. The SDK delegate and application facade have offline tests. Real SDK informational checks of signed feeds and stable/preview selection passed using isolated fixture identities and loopback transport on arm64 and x86_64 (Rosetta on the test host). Standalone SDK archive download, signature rejection, replacement, relaunch and cancel/retry fixtures passed on both CPU binaries. The complete production AppUpdates startup/KVO/pending-install lifecycle and real hardware-service coordination remain unverified. Automatic-update parity is not established. See [Sparkle setup](https://sparkle-project.org/documentation/) for its publishing and signing requirements.


### Local signed feed preparation (work in progress)

This is a work-in-progress maintainer tool in a source checkout, not a publishing command. Supply the current published signed appcast with `--previous-feed <appcast.xml>` when preparing an update. Its signature is verified with the same expected public key before any historical XML is parsed. A checkout containing `updates/appcast.xml` refuses preparation when this option is omitted. The tool does not fetch or confirm the latest GitHub feed; the maintainer must supply the current file. It never reads or generates deployment private keys, invokes a signing tool, accesses Keychain, uploads files or calls GitHub APIs.

After building with the intended **public** update key and packaging frozen artifacts, use `python3 Scripts/prepare-update-feed.py prepare --archive <universal.zip> --signature <archive-Ed25519-signature> --public-key <base64-public-key> --version <version> --build <build> --channel <stable-or-preview> --published <UTC-timestamp> --notes <English-notes-file> --output <new-directory>`. The timestamp uses `YYYY-MM-DDTHH:MM:SSZ`. The archive signature is supplied by the publisher's separate signing environment.

Preparation verifies the signature using CryptoKit, audits the built universal app and its matching update public key/policy, and checks every archive member against the verified package inputs, including file modes and framework aliases. A mismatch fails before writing output. It emits `appcast-unsigned.xml` and a public `signing-request.json`. The appcast targets the universal ZIP, supports both CPU families, sets macOS 13 as the current package floor, marks previews explicitly, and embeds escaped plain-text release notes. No remote release-note file is used.

Have the publisher's separate signing environment produce a detached Ed25519 signature over the **exact unchanged bytes** of `appcast-unsigned.xml`. Then run `python3 Scripts/prepare-update-feed.py finalize --public-key <expected-base64-public-key> --prepared <directory> --signature <feed-signature> --output <new-appcast.xml>`. Finalization requires the expected public key explicitly, checks that the request matches it, and verifies the historical signature again along with the merged template, byte count, SHA-256 and new signature before appending the [Sparkle signed-feed envelope](https://github.com/sparkle-project/Sparkle/blob/2.9.6/common_cli/Signing.swift). Existing preparation directories and final files are refused. The output remains local; a successful check does not prove publication, SDK selection, replacement or relaunch.

Stable and preview entries remain in one feed. New releases must advance both version and build number, keeping SDK build ordering consistent with semantic version selection. Same-version rebuilds and out-of-order backports are refused; they require a separate version/feed strategy. A preview can be promoted to stable with its original version, build, archive signature and byte count. A stable entry cannot be demoted to preview. Existing entries must use this tool's supported template, canonical official archive URLs, escaped inline notes and full-application policy; duplicate versions/builds and unsupported XML fields are rejected even if the old feed has a valid signature.

History is ordered by descending build and limited to 100 entries and 2 MiB. Pruning removes the oldest unprotected entries while retaining the entry being prepared and the latest stable and preview entries. Older schema-1 signing requests remain finalizable; new schema-2 requests carry the signed previous feed so history authentication can be repeated during finalization. The source-level and offline cryptographic checks are complemented by real SDK informational and disposable-app installation fixtures described in [verification](TESTING.md). They do not establish a complete production-app or privileged-service update acceptance.

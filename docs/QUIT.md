# Quit and discharge recovery

Ordinary monitoring-only quit remains immediate. When the app owns charge, sleep-assertion or LED work, Quit first prepares that session for exit. Policy refreshes and new in-app hardware changes pause during preparation. For the ordinary charge backend, the existing quit setting decides whether charging is restored or inhibited after exit; that inhibition request also releases active adapter discharge. LED restoration and the app's idle-sleep assertion are cleaned up independently, with errors reported.

After this app has successfully requested active discharge, a successful helper response alone is insufficient. The app waits for the OS to report external power, or battery power with an explicitly absent physical adapter. Safe observations must remain stable for at least half a second, with no sampling gap longer than one second. Longer gaps reset that confirmation. Missing properties, unknown sources and continued battery use with a connected/unknown adapter cannot prove recovery. Time uses system uptime rather than calendar time.

The wait lasts at most 15 seconds before asking for a decision. Cleanup failures also ask for a decision. Polling stops while that decision is pending and restarts only on retry. **Retry** repeats cleanup and starts a fresh wait. **Cancel Quit** keeps the app open and disables charge control; it does not automatically resume discharge or calibration. Calibration requires explicit continuation. Closing the quit window also cancels. **Exit Anyway** is offered only after failure/timeout and may leave recovery unconfirmed; a brief display interruption is possible and the helper may still need its heartbeat timeout to release a non-retained session. Cancel Quit now attempts to restore ordinary charge state, including retained inhibition requested during preparation. A failed or ambiguously acknowledged restore keeps recovery responsibility and the next quit retries it; re-enabling control also requires restoration first. Ordinary cancellation stores its recovery intent before the restore request. On a later startup, a stored intent disables control and retries restoration. The marker clears only after helper acknowledgement and a successful configuration save; failure keeps it pending and blocks new charge/LED grants. Portable backups exclude this operational marker. Storage failure can prevent durability, and older clients do not implement this marker. A clean cancellation does not repeat hardware cleanup. These acknowledgements do not prove physical adapter/display recovery. Numeric exit now prepares the selected limit while retaining the helper journal. Cancellation before final commit restores the captured original values. Final commit relinquishes the journal; after its delivery starts, an ordinary restore acknowledgement cannot prove rollback. A lost final reply offers retry of that same commit or explicit unconfirmed exit, and disables Cancel Quit rather than claiming recovery. The app never guesses an unrestricted value.

This uses [AppKit deferred termination and its required reply](https://developer.apple.com/documentation/appkit/nsapplication/reply%28toapplicationshouldterminate%3A%29). OS power-source confirmation uses [IOPSGetProvidingPowerSourceType](https://developer.apple.com/documentation/iokit/iopowersources_h/1810316-iopsgetprovidingpowersourcetype); a physically connected adapter is distinct from the source currently powering the computer. The helper uses fixed bounded commands and its existing watchdog; numeric preparation retains that watchdog responsibility until commit.

A native fake-only harness has exercised real AppKit delayed termination and its retry/cancel/explicit-exit choices. Those harness results do not establish physical discharge recovery, display transitions, actual sleep/logout/shutdown, interactions with external controllers or forced termination. Separately authorized ordinary charging tests and the basic daily pilot are recorded in [hardware evidence](HARDWARE.md); they do not validate retained inhibition across service shutdown or power-off. Force Quit and power loss cannot run this application-level cleanup. See [verification](TESTING.md) and [status](STATUS.md).

Development helper source adds a distinct `firmwareExit:preparedV1` extension. Preparation releases inflow-off/sleep protection, applies the selected target while retaining the existing journal and watchdog responsibility, and rejects replacement charge plans. Restoration cancels preparation using captured original values. Only a matching transaction commit relinquishes the journal. Duplicate commit acknowledgement is accepted only before a new charge session/reset; helper restart discards the in-memory transaction identity and recovers the existing same-boot journal. The app uses this extension during exit preparation and commits only at the final termination decision. A matching updated helper is required; an older helper is rejected before any irreversible exit command. Before commit delivery, cancellation remains available. After a lost commit reply, retry confirms the same transaction without preparing a new target; explicit unconfirmed exit remains available. Helper restart loses the in-memory commit receipt, so the app cannot infer whether a prior commit succeeded from an ordinary restoration acknowledgement. A committed target cannot be undone through ordinary restore; this extension does not change that boundary.

While the confirmation dialog is alive, the app renews an acknowledged numeric preparation every five seconds using the same target and transaction identity. The helper accepts that retry without a new register write. Power-source sampling still stops while a decision is pending. A renewal failure stops automatic retries, presents a decision and permits cancellation before final commit. An unresponsive or terminated client stops renewing, leaving the normal helper watchdog responsible for original-value restoration.


## App exit, service shutdown and power-off

These are separate lifetimes. Current source implements the following paths:

| Event | Implemented behavior | Evidence boundary |
| --- | --- | --- |
| Ordinary app quit with retention off | The app requests owned-state restoration. | A successful service reply is not a physical charging observation. |
| Ordinary app quit with retention on | The app requests retained inhibition. Published 0.3.57 uses a live retained lease outside its normal 45-awake-second expiry; the newer protocol below separates preparation and confirmation. | Retention depends on the helper continuing to run; it does not guarantee inhibition after service shutdown, crash, reboot or power-off. |
| Graceful helper termination | Published 0.3.57 attempts owned charge, LED and sleep restoration. Newer source can retain explicitly confirmed ordinary inhibition as described below. | Restoration can fail or be interrupted; this is not a tested OS shutdown sequence. |
| Numeric app quit | The app stages the phase-derived target with a transaction identity, retains recovery responsibility during preparation, then explicitly commits at final termination. Successful commit relinquishes ownership. | An acknowledged commit is not proof that the hardware preserves that target after power-off. Ordinary quit/sleep switches do not replace the numeric projection. |
| Sleep and wake | The helper's IOKit observer handles sleep admission, sleep entry and wake. | Its powered-on notification is a wake callback, not a boot or shutdown acceptance test. There is no separate power-off callback in this observer. |

The app uses the same deferred termination path for normal Quit and termination requested by macOS; current source does not identify those as separate shutdown policies. An ordinary recovery record belongs to one boot session. A later helper instance attempts recovery within that same boot, while a different boot discards stale ownership records without replaying their hardware writes. This protects against treating a previous boot's state as current ownership; it does not establish boot-time charge policy takeover.

## Ordinary prepared exit — development source after 0.3.57

Matching app/helper source negotiates the independent `ordinaryExit:preparedV1` capability. When ordinary “stop charging on quit” is selected, preparation requests inhibition through the existing fixed-key planner, releases adapter discharge and sleep protection, and keeps the original-value journal. Each preparation has a canonical UUID. Identical retries renew the awake watchdog without repeating hardware writes; another preparation cannot replace a pending one. Competing ordinary/numeric control requests are refused until restore or final confirmation.

Only the app's final termination decision sends the matching confirmation. A confirmed exit changes the live lease to retained. During graceful SIGTERM/SIGINT termination, the helper then leaves the already-inhibited charge state and its recovery journal in place while independently attempting LED and sleep cleanup. An unconfirmed exit or pending charge recovery instead attempts original-value charge restoration. A new charge action or explicit restore retires the old confirmation; a new preparation uses a new identity. Old identities cannot confirm that new preparation.

Ordinary confirmation does not discard the journal. Cancel Quit therefore remains recoverable through explicit restoration even if the confirmation reply was lost; it disables app control and retains the existing durable retry marker until acknowledgement and configuration persistence succeed. A newly started helper restores the remaining original-value journal within the same boot before accepting new charge requests. Different-boot stale records still are not replayed. Service removal still requires completed recovery. Nothing here establishes firmware persistence after power-off or automatic takeover after reboot.

An older helper does not advertise the capability. The app preserves the published live-helper retain request for that helper; it does not claim the new graceful-service-exit behavior. Installing source alone cannot upgrade a running service. The basic daily pilot remains on its reviewed service and is unaffected by these source-only changes.

Validation includes 300 core methods, an actual model fixture with injected requests, and the production ordinary planner/journal with injected registers on arm64 and x86_64 on the current host. These checks cover retained originals, discharge cleanup, committed versus uncommitted service cleanup, same-boot recovery and external changes. They do not terminate the real service, mutate SMC, or exercise physical shutdown/reboot.
